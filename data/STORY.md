# Редактирование истории

Сценарий кампании «Последний носитель» хранится в JSON. Отдельную Markdown-версию реплик и глав не вести. Этот документ описывает формат и порядок редактирования; сведения о работе мобильного приложения находятся в [RULES.md](../docs/RULES.md).

## Где менять данные

| Файл | Ответственность |
|---|---|
| [story.json](story.json) | Авторский сценарий: главы, встречи, исходные реплики, выборы, правила сохранения решений и пояснения замысла |
| [story-preview.json](story-preview.json) | Проверенный граф окон: точные реплики, варианты ответа, условия, эффекты, переходы, повторы и поражения; используется стендом и мобильным компилятором |
| [story-gameplay.json](story-gameplay.json) | Игровые настройки: услуги, сюжетные награды, развитие голоса, условия доступности реплик и прокачки |
| [characters.json](characters.json) | Идентичность, имена, портреты и ориентация сюжетных персонажей |
| [map-points.json](map-points.json), [maps.json](maps.json) | Типы занятий, значки и фоны глав |
| [journey-rules.json](journey-rules.json) | Уровни противников, стартовое здоровье первого босса, экипировка, режим боя и доступность кузниц |

`story-preview.json` поддерживается как разобранный граф, а не автоматически пересоздаётся из авторского текста. Одного изменения реплики в `story.json` недостаточно для изменения игры: её нужно согласованно обновить в графе и, при наличии, в `dialogueOverrides` игровых настроек.

`tools/compile-story.py` соединяет эти JSON в `mobile/content/generated/story-runtime.json`. `mobile/scripts/sync_content.py` компилирует сценарий и синхронизирует мобильный контент. Производные файлы в `content/generated` не редактировать и не коммитить. [Стенд истории](../story-preview/README.md) отдельно исполняет граф проверки и не является игровым клиентом.

## Содержимое авторского сценария

- `characters` и `speakers` связывают реплики с каталогами персонажей и существ. Эпизодические собеседники имеют устойчивые ID. Один персонаж сохраняет образ между сценами и повторами; разных людей нельзя объединять по общей роли «пленник» или «наёмник».
- `chapters` и `scenes` задают пролог, шесть глав, окончательный выбор, три концовки и повторы. `next` обозначает продолжение после завершения действий этапа.
- `state`, `conditions` и `persistence` задают память решений. `null` означает отсутствие принятого решения. Сюжетные решения, раскрытые личности, выполненные события и полученные награды сохраняются при поражении.
- `presentation` определяет стороны портретов, человеческие маски и границу знания об аттракторе.
- `attractor` описывает источник наполнения; численные пороги находятся в `story-gameplay.json`.
- `defeat` содержит тексты перерождения, условия раскрытий и сообщение о потерянных осколках.
- `authoringReferences` хранит синопсис, внутренний вопрос путешествия, пояснения остановок, ресурса и перерождения, последствия решений, манеру голоса и ограничения целостности. Это авторские пояснения, не готовые окна интерфейса.
- `source.dependencies` фиксирует проверенные редакции лора, анкет и каталогов. Авторский JSON не ссылается на внешний документ с копией сценария.

`story.json` остаётся `status: authoring`, `runtimeEnabled: false`: его инструкции нельзя напрямую показывать игроку или исполнять как окна. Godot работает с отдельно скомпилированным графом. Этот флаг не означает отсутствие сюжетной кампании в мобильной игре.

## Формат блоков и переходов

`script` сохраняет порядок авторской сцены. Готовая речь — `dialogue`, закадровый текст — `narration`, выбор — `choice`, явное действие — `action`. Блоки `encounterInstruction`, `interfaceInstruction`, `conditionalInstruction`, `choiceInstruction` и `instruction` имеют `display: false`. Их `sourceText` может сохранять исходную разметку отдельного указания, но не требует внешнего Markdown-документа.

Инструкцию нужно разрешить в узлы графа: окно, выбор, эффект, бой, награда или завершение. Неизвестная связь или неназначенный портрет блокируют экспорт. `null` в `creatureId` при `kind: human` означает человека, а не случайное существо.

В графе узел имеет `id`, `scene`, `kind`, `text`, `next`, при необходимости `speaker`, `when`, `effects`. Варианты `option` связаны с выбором через ID. `responsePlan` авторского блока исполняется только для выбранного варианта; произнесённый ответ героя показывается отдельным окном, затем следует ответ собеседника и общее продолжение. Меню вопросов возвращается после ответа; явно обозначенный выход заканчивает разговор.

Условия `when` должны охватывать всю соответствующую последовательность. Взаимоисключающие варианты нельзя показывать подряд; складывающиеся последствия обозначаются отдельно. Когда реплики зависят от прежнего значения состояния, условие оценивается до применения эффектов. Эффекты решения, отметка выполнения и сохранение применяются атомарно; повторное открытие не выдаёт награду снова.

## Правила текста и показа

- Сохранять мрачное фэнтези, конкретные образы и разные голоса персонажей. Недосказанность оставлять для тайн; текущую задачу, условия выбора и существенные последствия объяснять прямо.
- Писать естественную, понятную речь: из просьбы должно быть ясно, что именно нужно сделать, из ответа — на какой вопрос он отвечает. Называть предмет, человека или действие, если местоимение или образ допускает разные толкования. Не заменять объяснение афоризмом; лучше добавить короткое уточнение.
- При редактуре читать весь разговор вместе с вариантами ответа, а не отдельную реплику. Существенный поступок (например, убийство пленника или продажа лекарств) должен быть понятен до выбора. Сохранять характер говорящего и не приписывать герою знания, которых он ещё не получил.
- Одно окно содержит одну реплику или небольшой связный фрагмент обстановки. Длинное объяснение разбивать на несколько окон. При смене места или важном действии добавлять конкретный закадровый текст; служебная заметка не заменяет сообщение игроку.
- Каждое отображаемое предложение заканчивается знаком препинания внутри `text`, включая произносимые ответы. Подписи действий не требуют точки.
- Речь героя показывается с его портретом слева, остальных говорящих — справа. Закадровое повествование, найденные записи и неясные ощущения не наследуют портрет предыдущего собеседника. Одна реплика — один говорящий.
- Аттрактор говорит от своего имени с изображением камня справа. Его голос не слышен другим персонажам автоматически. Пока голос молчит, нельзя показывать его портрет или реплики как полноценный разговор.
- В прологе герой знает условия найма. Название, изображение и назначение груза раскрываются только в обязательной сцене 1.2 после `1.2.cargo-explanation`. Это знание сохраняется при смерти. Ранние сообщения поражения не раскрывают причину возвращения.
- До разоблачения использовать известную герою роль и человеческую маску персонажа. Имя вида и раскрытый портрет появляются только после соответствующего события.
- Кнопки действий не превращать в речь героя. Если выбор означает существенный поступок, обозначать его прямо. Пропуск текста должен останавливаться на выборе; автоматических ответов и автоматической концовки нет.
- Называть ресурс «осколки», при первом объяснении — «осколки сознания Логоса». «Душа» остаётся понятием лора. Доступный запас героя и наполнение аттрактора различаются.
- Не назначать противникам конкретное оружие в сцене или портрете: его генерирует игра. Описывать вид, роль и нейтральные действия; природные признаки существа допустимы.
- Учения персонажей не выдавать за доказанную истину мира. Не добавлять числовые характеристики или новые механики в художественную реплику; баланс менять в соответствующем каталоге.

## Согласованность прохождения

Переходы, порядок наград, повтор после смерти, память решений и финальный выбор определяются [RULES.md](../docs/RULES.md). При редактировании сверять `authoringReferences.decisions`, `authoringReferences.integrity`, условия концовок и повторов; не терять позднее признание Асте, различие продажи и возвращения семян, человеческие маски и одноразовые последствия.

Встреча `kind: human` с `creatureId: null` означает человека; `kind: creature` ссылается на конкретный вид. Сценарий не назначает случайную экипировку. Образы согласовывать с [лором](../docs/LORE.md), [бестиарием](../docs/CREATURES.md) и [персонажами](../docs/CHARACTERS.md).

## Мобильное исполнение

Компилятор соединяет авторский сценарий, граф, каталоги и игровые настройки, вставляя границы обычных наград. `Game.story` хранит узел, сцену, снимок входных условий, решения, выполненные эффекты, выданные награды, раскрытия, наполнение, выбранные встречи и число повторов. Условия `dialogueOverrides` читаются из конфига, а не из списка специальных ID в клиенте.

Номер формата игры задаёт `story-gameplay.json.saveVersion`; обработка файлов и резервных копий находится в мобильном хранилище. Изменение чисел врагов требует согласования `journey-rules.json.enemyBalanceVersion`; уже выданную колоду и раскрытый бой нельзя незаметно пересоздавать. Отпечатки и производный runtime обновляются после содержательной сверки исходников.

## Порядок изменения сценария

1. Найти сцену и её устойчивые ID в авторском JSON и графе. Для изменения существующего текста сохранить ID; новые ID назначать только новым блокам и вариантам.
2. Согласованно изменить `story.json` и соответствующие узлы `story-preview.json`, включая вложенные ответы, условные варианты, повторы и поражения. При изменении структуры проверить `scenes`, `tree`, `next`, `options` и переходы награды. Числа и игровые переопределения менять в `story-gameplay.json`.
3. Проверить каталоги говорящих, встреч, занятий и карт. Для новых изображений обновить пути в данных и профильную арт-документацию; проверить файлы в `images`, затем синхронизировать мобильные копии.
4. Провести содержательную сверку изменённых сцен и последствий. Только после неё обновить SHA-256 изменённых записей `story.json.source.dependencies`, затем отпечаток `data/story.json` и остальных изменённых источников в `story-preview.json.sources`. Не обновлять отпечатки вместо переноса текста. В `sources` графа входят JSON-каталоги, не копия сценария в Markdown.
5. При изменении графа повышать его `revision`; при изменении мобильных правил — `story-gameplay.json.revision`. Изменение только пояснений или отпечатков без изменения исполняемого графа не требует сброса прохождения.
6. Запустить проверки ниже. При изменении переходов или механики также проверить мобильную кампанию. Не поддерживать вторую ручную версию сюжета в `docs`; читать и проверять реплики через стенд истории.

## Проверки

Из корня проекта:

```sh
npm run check:story
npm run test:story
npm run check:map-points
npm run check:story-runtime
npm run test:story-runtime
npm --prefix story-preview test
python3 mobile/scripts/sync_content.py
```

Для проверки мобильных переходов после синхронизации:

```sh
"$GODOT_BIN" --headless --path mobile --script res://tests/campaign.gd
"$GODOT_BIN" --headless --path mobile --script res://tests/story_ui.gd
```

Настройка Godot — в [mobile/README.md](../mobile/README.md). `check:story -- --runtime` намеренно отклоняет прямое исполнение авторского JSON с инструкциями. Для настоящего мобильного экспорта использовать `check:story-runtime`. Проверки ссылок и отпечатков не заменяют прохождение ветвей: после сюжетных изменений проверять условия, повтор после смерти, отсутствие повторных наград и все три концовки.

## Кавычки реплик

Все произносимые реплики (`dialogue`) и варианты ответа с `selectionType: speech` заключаются в «ёлочки» непосредственно в данных, включая условные варианты текста. Вложенные кавычки — „лапки“. Рассказчик, инструкции и названия действий остаются без внешних кавычек.
