# Герои Орвеска

## Структура и границы

- Единственный игровой движок — GDScript в `mobile/game`; общий контент хранится в `data` и `images`. Вторую реализацию игровой механики для тестов не создавать.
- Каноническая палитра — `mobile/content/palette.json`; синхронизация доставляет её в мобильные ресурсы без изменения цветов. Каталоги и палитру не дублировать вручную.
- `story-preview` — отдельный браузерный инструмент для сценария; его JavaScript и CSS не являются игровым клиентом. Node.js нужен инструментам сценария, но не сборке Android.
- Не раздавать и не коммитить `data/sessions`. Не читать и не редактировать корневой `ideas.md`: это личные заметки пользователя.

## Документация

- Перед изменением игровой механики читать `docs/RULES.md`: это единственное описание правил, состояний игры, эффектов навыков, экипировки, наград и кампании. Правила не дублировать в лоре, каталогах, README или других документах.
- Перед изменением расчётов или баланса читать `docs/FORMULAS.md`: здесь собраны все игровые формулы, округления и численные параметры. Исполняемые значения меняются в `data` и `mobile/game`; документ обновлять в той же задаче.
- Перед генерацией или редактированием изображений читать `docs/ART_DIRECTION.md` и просматривать указанные референсы. Это единое художественное направление для персонажей, существ, предметов, действий, значков, карт и фонов. Отдельные документы художественного направления не создавать.
- В `docs` хранить действующие требования, лор и каталоги. Не сохранять историю заменённых механик, миграций, генераций и исследовательских итераций как текущие правила.
- **Отчёты испытаний не размещать и не коммитить в репозиторий**: результаты симуляций, сравнительные исследования, логи, CSV/JSON с измерениями, скриншоты проверок и временные отчёты сохранять во временном каталоге ОС либо в явно указанном пользователем месте вне репозитория. Скрипты проверки, тесты и необходимые воспроизводимые фикстуры остаются в проекте. Принятые выводы отражать как текущие правила или параметры, без переноса отчёта.

## Синхронизация данных, документации и изображений

- При добавлении, изменении, переименовании или удалении сущности согласованно обновлять `data`, её художественное описание в `docs`, игровые правила/расчёты при их изменении и ссылки на изображения. Проверять ID, названия, свойства, описания и актуальность иллюстраций.
- Каталоги: предметы — отдельные каталоги `docs/WEAPONS.md`, `docs/SHIELDS.md`, `docs/ARMOR.md`, `docs/FOOTWEAR.md`, `docs/JEWELRY.md`, `docs/BASIC_EQUIPMENT.md`, существа — `docs/CREATURES.md`, навыки — `docs/SKILLS.md`, базовые действия — `docs/BASE_ACTIONS.md`, природные действия — `docs/CREATURE_ACTIONS.md`, именные персонажи — `docs/CHARACTERS.md`, точки карты и превью — `docs/MAP_POINTS.md`. Эти документы хранят образы и связи с данными, а не отдельные версии игровых правил или формул.
- Лор — `docs/LORE.md`. Карты и фоны — `data/maps.json`, оформление и превью — раздел карт `docs/ART_DIRECTION.md`; типы точек — `data/map-points.json`. Не записывать координаты и связи игрового графа в художественный пресет.
- Изображения хранить в соответствующем каталоге ассетов, в Markdown использовать относительные ссылки и компактные превью; не копировать изображения в `docs`. При переносе или замене обновлять ссылки в данных и клиентах. Различать подготовленные и подключённые изображения.
- Запросы и метаданные происхождения актуальных изображений хранить в `art-prompts`; они не заменяют художественное направление и не служат хранилищем отчётов испытаний.
- Перед завершением проверять файлы по ссылкам, JSON и соответствие описаний данным. Мобильные копии обновлять по `mobile/README.md`; производные файлы вручную не редактировать.

## Сценарий

- Перед изменением сценария читать `data/STORY.md`. Согласованно редактировать `data/story.json`, `data/story-preview.json` и при необходимости `data/story-gameplay.json`; сохранять ID и обновлять отпечатки только после содержательной сверки.
- Пояснения замысла находятся в `story.json.authoringReferences`, правила редактирования — в `data/STORY.md`, правила прохождения — в `docs/RULES.md`. Отдельную Markdown-копию реплик и глав не вести.
- Godot исполняет производный `story-runtime.json`; авторский `runtimeEnabled: false` сохраняется.
- После изменения сценария запускать `npm run check:story`, `npm run test:story`, `npm run check:story-runtime`, `npm run test:story-runtime`, `npm --prefix story-preview test`; затем синхронизировать мобильный контент.

## Механика и проверки

- Не добавлять инвентарь без отдельного запроса. Единственный действующий режим боя — `free`; все новые проверки баланса выполняются в нём. Применение правил сверять с `docs/RULES.md` и `docs/FORMULAS.md`.
- Определения фигур менять у владельца в `data`: предметы — `figures`, навыки — `figure`, базовые действия — `base-actions.json`, природные — `creatures.json`. Формат — `data/FIGURES.md`; ограничения существ — `data/CREATURES.md`; типы урона — `data/damage-types.json`.
- Не вводить проверки конкретных ID предметов или навыков в генерацию фигур. Новая механика расширяет типизированный интерпретатор; новый контент — конфиг. Пассивные бонусы не записывать в базовые характеристики.
- Корневой `npm run check` проверяет сценарий, точки карты и компиляцию сценария. После изменения механики запускать профильные Godot-проверки по `mobile/README.md`; результаты прогонов держать вне репозитория.
- `mobile/tests/fixtures/combat-reference.json` — фиксированные входные данные и ожидаемые результаты боевых проверок. Это исходники тестов: хранить в Git, не перегенерировать ожидаемые значения проверяемым движком. При изменении правил сверять их с `docs/FORMULAS.md`, осознанно обновлять затронутые примеры и добавлять проверки новых механик.

## Пользовательские правила

- Название pull request: `<номер тикета>: <точное название тикета>` из канонического Tracker. После создания/переименования перепроверить сохранённый заголовок целиком.
- Не включать автопубликацию pull request без прямого запроса.
- Комментарии в Tracker и Arcanum начинать с `Ответ AI:`.
